00 L'exam en vrai

L'Exam Rank 02, c'est un chrono qui tourne et quatre niveaux à franchir dans l'ordre (0 → 3), chacun un cran plus exigeant que le précédent. À chaque niveau, un seul exercice tombe au hasard : tu le codes, tu rends, et la moulinette juge instantanément — verdict binaire, pas de « presque bon ». Tu réussis → niveau suivant. Ce qui se joue vraiment n'est pas ta capacité à trouver l'algorithme le plus élégant, mais ta capacité à reconnaître un motif connu et à le ressortir vite, sans faute.

Les règles de la moulinette (à connaître par cœur)

La moulinette ne juge pas ton intelligence, elle juge une correspondance. Elle compare ce que ton binaire produit à ce qu'elle attend, caractère par caractère, et elle ne fait aucune concession. Six points reviennent à chaque exercice ; ce sont eux, bien plus que la difficulté algorithmique, qui décident si tu passes ou si tu recommences.

  • Nom de fichier exact. Si le sujet dit ft_split.c, ton fichier s'appelle ft_split.c — à la lettre près. Pas de .h en plus, sauf si le sujet le réclame explicitement.
  • Prototype exact. Type de retour, nom, ordre et type des paramètres : recopie mentalement le prototype du sujet plutôt que de le reconstruire de mémoire. Une virgule ou un const oublié suffit à tout casser.
  • Uniquement les fonctions autorisées (ligne Allowed functions). Souvent write seul, parfois malloc en plus, parfois None — c'est-à-dire rien, tu te débrouilles avec le langage nu.
  • Compilation stricte : -Wall -Wextra -Werror. Le moindre warning transforme la compilation en échec, donc en zéro. Une variable déclarée et jamais utilisée, une comparaison entre un int signé et une taille unsigned : ce sont des classiques qui piègent même quand l'algo est parfait.
  • Zéro segfault. Une seule sortie mémoire suffit à tuer l'exercice, même si le résultat affiché juste avant était correct. Le crash écrase tout.
  • Sortie exacte au caractère près. La moulinette compare via cat -e, qui rend visible ce que ton terminal cache : le $ marque chaque fin de ligne. Un espace en trop, un \n manquant ou dupliqué, et c'est un échec silencieux — ton programme « avait l'air » de marcher.
Réflexe

Prends l'habitude de toujours passer ta propre sortie dans | cat -e avant de rendre. Le piège numéro un de l'exam n'est presque jamais l'algorithme — c'est un \n mal placé ou un espace fantôme, invisibles à l'œil nu dans un terminal classique mais fatals devant la moulinette.

« Fonction » ou « Programme » ? La distinction qui change tout

Avant même de réfléchir à l'algorithme, une seule phrase du sujet détermine la forme entière de ta réponse. Lis-la en premier, elle change tout ce qui suit :

  • « Write a function… » → tu écris seulement la fonction demandée, sans main. La moulinette possède déjà son propre main pour t'appeler et vérifier le résultat. Ajoute un main par réflexe et tu obtiens une double définition qui casse la compilation — un des pièges les plus bêtes, et les plus fréquents, de l'exam.
  • « Write a program… » → à toi d'écrire un main(int argc, char **argv) complet : lire les arguments, produire le résultat, gérer le \n final. Rien n'est fourni.

01 La boîte à outils

Ce qui donne l'impression que l'exam couvre « 55 exercices différents » est une illusion d'optique : 90 % d'entre eux se construisent avec les 5 mêmes briques, recombinées. Apprends-les jusqu'à pouvoir les réécrire les yeux fermés, sans réfléchir — c'est le temps que tu gagnes sur l'algorithme lui-même, et les fautes de frappe idiotes que tu élimines d'office.

write, ft_putchar, ft_putstr

La quasi-totalité des « programmes » de l'exam n'autorisent que write — pas de printf, pas de confort. Sa signature mérite d'être connue par cœur : write(1, ptr, taille), où 1 désigne la sortie standard (le terminal). Tout le reste — afficher un caractère, une chaîne, un nombre — n'est qu'une variation autour de cet unique appel système.

toolbox.c
// afficher un seul caractère
void ft_putchar(char c)
{
    write(1, &c, 1);
}

// afficher une chaîne, caractère par caractère
void ft_putstr(char *str)
{
    int i = 0;

    while (str[i])
    {
        write(1, &str[i], 1);
        i++;
    }
}
Astuce

Pour un \n final, le plus simple : write(1, "\n", 1);. Pas besoin de variable.

À toi de jouer

Voir la réponse

Afficher un nombre entier (le classique récursif)

Sans printf, afficher un int revient à l'afficher chiffre par chiffre, ce qui n'est naturel que dans un sens (du poids fort vers le poids faible) alors qu'on ne les calcule facilement que dans l'autre (via % 10, du poids faible vers le fort). La récursion résout élégamment ce conflit : on s'appelle sur le reste de la division avant d'afficher le chiffre courant, ce qui inverse l'ordre gratuitement, sans buffer ni tableau. Le piège absolu à connaître : INT_MIN vaut -2147483648, et sa valeur absolue positive n'existe tout simplement pas dans la plage d'un int. Toute tentative de -n dessus est un comportement indéfini. La parade est mécanique : copier n dans un long avant de manipuler le signe.

ft_putnbr.c
void ft_putnbr(int n)
{
    long nb = n;           // long => on peut négliger l'overflow de INT_MIN

    if (nb < 0)
    {
        write(1, "-", 1);
        nb = -nb;
    }
    if (nb >= 10)
        ft_putnbr(nb / 10);
    ft_putchar(nb % 10 + '0');   // chiffre -> caractère
}

chiffre + '0' transforme 0..9 en '0'..'9'. Retiens ce couple : c - '0' (caractère → chiffre) et d + '0' (chiffre → caractère).

Vérifie ta compréhension

Sans exécuter : que va afficher ft_putnbr(-2147483648) ? Et pourquoi la version naïve qui fait n = -n sur un int échouerait-elle ?

Voir la réponse

Elle affiche correctement -2147483648. La version naïve échoue car -(-2147483648) déborde la capacité d'un int (le max positif est 2147483647) : le résultat est indéfini. En copiant d'abord dans un long (long nb = n;), -nb tient sans problème.

main, argc, argv

Source d'erreurs bête et récurrente : argc compte le nom du programme lui-même comme premier argument. Donc quand le sujet parle d'« 1 argument » du point de vue de l'utilisateur, ça se traduit en code par argc == 2. Se planter de un ici ne provoque pas un crash spectaculaire — juste un programme qui n'affiche jamais rien, ou qui plante sur argv[1] quand l'utilisateur n'a rien fourni. C'est le genre d'erreur qu'on ne voit qu'en relisant la condition à froid.

program.c
int main(int argc, char **argv)
{
    if (argc == 2)          // exactement UN argument utilisateur
        traiter(argv[1]);
    write(1, "\n", 1);   // le \n final tombe dans TOUS les cas
    return (0);
}
Piège récurrent

« Si le nombre d'arguments n'est pas 1, affiche juste un \n ». En pratique : place le write(1, "\n", 1) à la fin, toujours exécuté, et n'affiche le contenu que si argc == 2. Un seul \n pour les deux cas.

Vérifie ta compréhension

Pour la commande ./prog "a" "b", combien vaut argc ? Et quelle condition écris-tu pour dire « l'utilisateur a passé exactement 2 arguments » ?

Voir la réponse

argc == 3 (le nom du programme compte pour 1). Pour « exactement 2 arguments utilisateur » → if (argc == 3). Règle générale : N arguments utilisateur ⇒ argc == N + 1.

malloc & chaînes allouées

Quel que soit l'exercice — ft_strdup, ft_split, ft_itoa — la mécanique de l'allocation ne change jamais, seul son contenu varie. Le schéma se déroule toujours dans le même ordre, et retenir cet ordre t'évite d'improviser sous pression : (1) calculer la taille nécessaire avant d'allouer quoi que ce soit, (2) appeler malloc avec cette taille, (3) vérifier immédiatement le retour, car un malloc qui échoue renvoie NULL et continuer dessus segfaulte, (4) remplir la zone allouée, (5) terminer par '\0' — sans quoi la chaîne n'en est pas une, et tout ce qui la lira ensuite ira lire au-delà de ce que tu as réellement écrit.

ft_strdup.c
char *ft_strdup(char *src)
{
    int   i = 0;
    int   len = 0;
    char  *dst;

    while (src[len])              // 1. taille
        len++;
    dst = malloc(sizeof(char) * (len + 1));  // 2. +1 pour le '\0'
    if (!dst)                     // 3. toujours vérifier
        return (0);
    while (i < len)               // 4. remplir
    {
        dst[i] = src[i];
        i++;
    }
    dst[i] = '\0';               // 5. terminer
    return (dst);
}
Le +1 qui sauve

Pour une chaîne de longueur len, on alloue len + 1 (place du '\0'). Pour un tableau de n pointeurs terminé par NULL (comme ft_split), on alloue n + 1. Oublier ce +1 = le bug n°1 de la piscine.

Vérifie ta compréhension

Tu veux dupliquer la chaîne "42". Combien d'octets passes-tu à malloc, et que se passe-t-il si tu oublies le +1 ?

Voir la réponse

3 octets : 2 pour '4' et '2', plus 1 pour le '\0' final. Sans le +1, tu écris le '\0' hors de la zone allouée (débordement) : comportement indéfini, souvent un segfault ou une chaîne qui « continue » dans la mémoire voisine.

atoi maison

Convertir une chaîne en int demande trois passes distinctes et dans cet ordre précis : ignorer les espaces et blancs de tête, repérer un ou plusieurs signes, puis accumuler les chiffres un par un jusqu'au premier caractère qui n'en est pas. C'est une brique qu'on réutilise telle quelle dans do_op, fprime, tab_mult et une bonne partie des exercices « maths » — la coder correctement une fois, la mémoriser, et ne plus jamais avoir à y repenser.

ft_atoi.c
int ft_atoi(const char *str)
{
    int i = 0;
    int sign = 1;
    int res = 0;

    while (str[i] == ' ' || (str[i] >= 9 && str[i] <= 13))
        i++;                       // espaces + tabs/retours
    while (str[i] == '+' || str[i] == '-')
    {
        if (str[i] == '-')
            sign = -sign;          // plusieurs signes possibles
        i++;
    }
    while (str[i] >= '0' && str[i] <= '9')
    {
        res = res * 10 + (str[i] - '0');
        i++;
    }
    return (res * sign);
}
Vérifie ta compréhension

Que renvoie ton ft_atoi sur la chaîne " -0042abc" ? Déroule mentalement les trois boucles.

Voir la réponse

-42. La 1re boucle saute les 3 espaces, la 2e lit le - (signe négatif), la 3e accumule 0, 0, 4, 2 puis s'arrête au a (non-chiffre). Les zéros de tête n'ont aucun effet, et tout ce qui suit un caractère non numérique est ignoré.

02 Les notions à maîtriser

55 noms d'exercices, mais à peine 9 notions derrière. C'est le vrai secret de cet exam : personne n'a le temps d'inventer un algorithme sous chrono, alors reconnais la famille à laquelle appartient l'énoncé, rappelle-toi son squelette, et n'improvise que sur le petit cœur qui change d'un exercice à l'autre.

Notion : Transformer argv[1] lettre par lettre

Exos concernés : rotone, rot_13, ulstr, alpha_mirror, repeat_alpha.
Squelette : vérifier argc == 2, parcourir la chaîne, transformer chaque caractère, \n final.

Toute cette famille repose sur une seule idée : en C, une lettre est un nombre. 'a' vaut 97, 'b' vaut 98, et ainsi de suite — donc « décaler une lettre dans l'alphabet » n'est jamais qu'une addition suivie d'un % 26 pour revenir au début quand on dépasse 'z'. Une fois cette bascule mentale faite (penser en positions, pas en lettres), rotone, rot_13, alpha_mirror et compagnie deviennent la même fonction avec une constante différente. La seule vraie question à te poser sur chacun : quelle est la formule qui transforme une lettre ? Et comme majuscules et minuscules n'occupent pas les mêmes codes ASCII, il faut toujours traiter les deux cas séparément, chacun ancré sur son propre 'a' ou 'A'.

rotone.c — décale chaque lettre de 1
int main(int argc, char **argv)
{
    int  i = 0;
    char c;

    if (argc == 2)
    {
        while (argv[1][i])
        {
            c = argv[1][i];
            if (c >= 'a' && c <= 'z')
                c = (c - 'a' + 1) % 26 + 'a';   // 'z' -> 'a'
            else if (c >= 'A' && c <= 'Z')
                c = (c - 'A' + 1) % 26 + 'A';
            write(1, &c, 1);
            i++;
        }
    }
    write(1, "\n", 1);
    return (0);
}

Une fois le squelette de rotone en tête, chaque variante ne change qu'une ligne — la formule du cœur : rot_13 décale de 13 au lieu de 1, c'est le même % 26, seule la constante change (et parce que 13 est exactement la moitié de 26, chiffrer deux fois de suite avec rot_13 te ramène au texte d'origine — c'est tout l'intérêt historique de ce chiffrement, popularisé dans les forums Usenet pour cacher des spoilers sans vraie cryptographie) ; alpha_mirror ne décale pas mais reflète, 'z' - (c - 'a') ; ulstr ne touche pas à la position dans l'alphabet mais à la casse, via c ^ 32 (ou +32/-32 selon le sens) ; repeat_alpha sort du cadre « une lettre en entrée, une lettre en sortie » en ajoutant une boucle interne qui réaffiche la même lettre autant de fois que sa position dans l'alphabet.

Le truc du miroir

Pour alpha_mirror, 'z' - (c - 'a') fonctionne parce que c - 'a' donne la distance de c depuis le début de l'alphabet (0 pour 'a', 25 pour 'z'), et soustraire cette distance à 'z' la retourne symétriquement (0 devient 'z', 25 devient 'a'). Pour repeat_alpha, retiens que l'énoncé numérote 'a' à partir de 1 et non de 0 : l'index est donc c - 'a' + 1 en minuscule, c - 'A' + 1 en majuscule — oublier le + 1 est l'erreur la plus commune sur cet exercice.

Vérifie la notion

Écris la seule ligne qui transforme une minuscule c selon rot_13 (décalage de 13, 'z'→'m').

Voir la réponse
cœur de rot_13
c = (c - 'a' + 13) % 26 + 'a';

Le % 26 gère le « rebouclage » quand on dépasse la fin de l'alphabet : 'z' (index 25) → (25 + 13) % 26 = 12 → 'm'. Sans ce modulo, tu obtiendrais un caractère complètement hors de l'alphabet (ponctuation, symboles) au lieu de reboucler proprement sur 'a'. Idem pour les majuscules, en remplaçant simplement 'a' par 'A' — les deux blocs ASCII sont indépendants, ne mélange jamais l'un avec l'autre dans la même formule.

Notion : Découper une chaîne en mots

Exos concernés : first_word, last_word, epur_str, expand_str, rev_wstr, rostring, str/rstr_capitalizer.
Idée maîtresse : un « mot » = suite de non-espaces. On avance avec deux réflexes : sauter les espaces, puis lire un mot.

Cette famille casse l'habitude prise avec la précédente : on ne parcourt plus caractère par caractère avec une seule boucle, on avance par blocs. Le motif à graver dans les doigts est une alternance à deux temps — une boucle qui avale les espaces, suivie d'une boucle qui avale un mot — répétée jusqu'à la fin de la chaîne. Tous les exercices de cette notion ne sont que des variations sur ce que tu fais pendant la deuxième boucle (afficher, compter, mémoriser une position) et sur ce que tu insères entre deux mots.

motif de parcours par mots
int is_space(char c)
{
    return (c == ' ' || c == '\t');
}

// ... dans une boucle :
while (str[i])
{
    while (str[i] && is_space(str[i]))   // 1. sauter les espaces
        i++;
    while (str[i] && !is_space(str[i]))  // 2. lire/afficher un mot
    {
        // write(1, &str[i], 1);  selon l'exo
        i++;
    }
    // ici : fin d'un mot -> gérer l'espace de séparation
}

epur_str (un espace entre mots, aucun au bord) : affiche un espace avant chaque mot sauf le premier — c'est la façon la plus sûre d'éviter tout espace en trop aux extrémités. expand_str : exactement le même principe, juste trois espaces au lieu d'un. first_word : le cas le plus simple de tous, tu affiches le premier mot puis tu t'arrêtes (return) sans même regarder la suite de la chaîne. last_word : à l'inverse, il faut aller jusqu'au bout — retiens la position de départ à chaque nouveau mot rencontré, celle du dernier mot vu sera la bonne quand la boucle se termine. rev_wstr / rostring : affichent les mots dans un ordre différent (souvent inversé), ce qui demande généralement de les parcourir une première fois pour les repérer, avant de les réafficher dans le nouvel ordre.

Piège capitalizer

str_capitalizer met la première lettre de chaque mot en majuscule, le reste en minuscule. La difficulté n'est pas la transformation elle-même mais la détection : un mot commence quand le caractère qui précède est un espace, ou quand on est au tout début de la chaîne — il faut donc garder en mémoire l'état du caractère précédent au fil de la boucle. Piège classique : un mot d'une seule lettre reste capitalisé (elle est à la fois la première et la dernière). Teste avec des chiffres collés aux lettres — le comportement attendu à la frontière chiffre/lettre est souvent sous-spécifié dans l'énoncé et vaut la peine d'être vérifié à la main.

Vérifie la notion

Dans epur_str (exactement un espace entre les mots, aucun aux bords), à quel moment affiches-tu l'espace de séparation, pour ne jamais en avoir un en trop au début ?

Voir la réponse

Tu affiches l'espace juste avant chaque mot, sauf le premier. Concrètement : tu sautes les espaces, et si tu es sur le début d'un mot et que ce n'est pas le tout premier mot affiché, tu écris un espace puis le mot. Un drapeau first (mis à 0 dès qu'un mot est écrit) suffit à distinguer le premier des suivants.

Notion : Ensembles de caractères

Exos concernés : inter, union, wdmatch, hidenp, search_and_replace.
Outil clé : un tableau de drapeaux int seen[256] pour marquer les caractères déjà vus (« sans doublons ») en O(1).

La tentation naturelle face à « est-ce que ce caractère a déjà été vu ? » est de reparcourir ce qu'on a déjà affiché à chaque nouveau caractère — ça marche, mais ça complique le code et multiplie les occasions de bug. L'astuce à retenir pour toute cette famille : puisqu'un char ne prend que 256 valeurs possibles, un simple tableau de 256 cases suffit à mémoriser « vu / pas vu » en temps constant, sans structure de données compliquée. C'est le même outil, décliné en marquage (union, inter) ou en parcours à deux indices synchronisés (wdmatch, hidenp).

union.c — chars de s1 puis s2, sans doublons
int main(int argc, char **argv)
{
    int seen[256] = {0};   // 256 = tous les codes de char (unsigned)
    int a = 0;

    if (argc == 3)
    {
        while (a < 2)               // parcourt argv[1] puis argv[2]
        {
            int i = 0;
            while (argv[a + 1][i])
            {
                unsigned char c = argv[a + 1][i];
                if (!seen[c])
                {
                    seen[c] = 1;
                    write(1, &c, 1);
                }
                i++;
            }
            a++;
        }
    }
    write(1, "\n", 1);
    return (0);
}

inter : n'affiche un caractère de s1 que s'il est à la fois présent dans s2 et pas déjà affiché — deux conditions, deux seen[256] ou une combinaison des deux, selon la formulation exacte du sujet. wdmatch / hidenp changent complètement d'outil : on cherche si s1 apparaît « caché » dans s2, c'est-à-dire dans le même ordre mais pas forcément consécutif. Deux indices i et j avancent en parallèle : quand s1[i] == s2[j], on fait avancer i en plus de j ; sinon on avance seulement j. Si i atteint la fin de s1 avant que j n'épuise s2, c'est gagné. search_and_replace : remplace une lettre par une autre dans argv[1], mais uniquement si les arguments qui désignent l'ancienne et la nouvelle lettre sont bien des caractères uniques — vérifier leur longueur avant de commencer est une étape à ne pas sauter.

Vérifie la notion

Pourquoi indexer seen[256] avec un unsigned char plutôt qu'un char ordinaire ? Quel bug guette si tu utilises un char ?

Voir la réponse

Un char peut être signé : pour un caractère accentué ou de code > 127, sa valeur devient négative. seen[-30] lit/écrit hors du tableau → comportement indéfini, souvent un segfault. En castant en unsigned char, l'index reste dans 0..255, exactement la taille du tableau.

Notion : Maths & nombres

Exos concernés : fizzbuzz, tab_mult, do_op, add_prime_sum, fprime, pgcd, lcm, print_hex, ft_atoi_base, is_power_of_2.

La famille la plus hétérogène de l'exam, mais aussi celle où printf est le plus souvent autorisé — ce qui change la donne : ici, la difficulté n'est presque jamais dans l'affichage, elle est entièrement dans la logique mathématique. Trois blocs reviennent sans cesse : la primalité (un nombre n'a que lui-même et 1 comme diviseurs), le PGCD/PPCM (l'algorithme d'Euclide, vieux de 2300 ans et toujours imbattable en simplicité), et les conversions de base (le principe du ft_putnbr récursif, généralisé à autre chose que 10).

Primalité (add_prime_sum, fprime)

test de primalité
int is_prime(int n)
{
    int i = 2;

    if (n < 2)
        return (0);
    while (i <= n / i)      // équivaut à i*i <= n, sans overflow
    {
        if (n % i == 0)
            return (0);
        i++;
    }
    return (1);
}

fprime décompose un nombre en facteurs premiers en réutilisant presque littéralement is_prime à l'envers : on essaie de diviser n par i à partir de 2, et tant que n % i == 0 on divise effectivement (en affichant i à chaque division), sinon on passe à i + 1. Le seul détail d'affichage à soigner est le séparateur * : il apparaît entre deux facteurs, jamais avant le premier — un drapeau « déjà affiché un facteur » suffit à le gérer proprement.

PGCD & PPCM (pgcd, lcm)

Euclide
// PGCD par soustractions ou modulo
unsigned int gcd(unsigned int a, unsigned int b)
{
    while (b)
    {
        unsigned int t = b;
        b = a % b;
        a = t;
    }
    return (a);
}
// PPCM :  lcm = a / gcd(a,b) * b   (si a et b non nuls)

Conversion de base (print_hex, ft_atoi_base)

print_hex convertit un nombre de la base 10 vers la base 16 : c'est exactement le même schéma récursif que ft_putnbr (diviser, se rappeler sur le quotient, afficher le reste au retour), sauf qu'on divise par 16 au lieu de 10, et qu'on n'affiche plus chiffre + '0' mais on va chercher le caractère correspondant dans la table "0123456789abcdef" — le reste de la division par 16 devient directement un index dans cette chaîne. ft_atoi_base fait le trajet inverse : pour chaque caractère lu, on détermine sa valeur numérique dans la base donnée (chiffres 0-9, puis lettres a-f valant 10 à 15, insensibles à la casse), et on accumule avec res = res * base + valeur — la même formule d'accumulation que ft_atoi, juste avec base à la place de 10. Le signe - ne compte que s'il est le tout premier caractère.

do_op

do_op autorise atoi et printf, ce qui en fait un des exercices les plus rapides à écrire une fois le piège repéré : récupère a = atoi(argv[1]), b = atoi(argv[3]), regarde le premier caractère de argv[2] pour savoir quel opérateur appliquer, puis printf("%d\n", ...). Le vrai piège n'est pas la logique mais la robustesse : une division ou un modulo par 0 est un comportement indéfini en C (souvent un crash). Observe ce que le sujet attend précisément dans ce cas — généralement, il faut détecter b == 0 avant l'opération et éviter le crash plutôt que de laisser le programme planter.

Notion : Manipulation de bits

Exos concernés : print_bits, reverse_bits, swap_bits, is_power_of_2.

Cette famille demande de descendre d'un niveau d'abstraction : on ne raisonne plus en « nombre », mais en suite de 8 bits individuels. Trois opérateurs suffisent à tout faire — >> pour amener un bit précis à la position 0, & pour l'isoler du reste, | et << pour reconstruire un résultat bit par bit. Une fois ces trois réflexes en place, les quatre exercices ci-dessous ne sont que des combinaisons différentes des mêmes trois opérateurs.

bits.c
// afficher les 8 bits, du plus fort au plus faible
void print_bits(unsigned char octet)
{
    int i = 7;

    while (i >= 0)
    {
        char bit = ((octet >> i) & 1) + '0';
        write(1, &bit, 1);
        i--;
    }
}

// inverser l'ordre des 8 bits
unsigned char reverse_bits(unsigned char o)
{
    unsigned char res = 0;
    int i = 0;

    while (i < 8)
    {
        res = (res << 1) | ((o >> i) & 1);
        i++;
    }
    return (res);
}

// échanger les deux quartets :  0xAB -> 0xBA
unsigned char swap_bits(unsigned char o)
{
    return ((o >> 4) | (o << 4));
}

// puissance de 2 : un seul bit à 1
int is_power_of_2(unsigned int n)
{
    if (n == 0)
        return (0);
    return ((n & (n - 1)) == 0);
}
À mémoriser

(x >> i) & 1 lit le i-ème bit d'un nombre — le décalage l'amène en position 0, le masque efface tout le reste. Moins intuitif mais tout aussi utile : x & (x - 1) éteint toujours le bit à 1 le plus bas de x (par exemple 0b1100 & 0b1011 = 0b1000). Conséquence directe : ce calcul ne peut valoir 0 que si x ne possédait qu'un seul bit allumé au départ — c'est exactement la définition d'une puissance de 2, d'où le test is_power_of_2.

Vérifie la notion

Voir la réponse
lecture d'un bit

On décale l'octet de 3 positions vers la droite (le bit visé arrive en position 0), puis & 1 masque tout le reste. Pour le n-ième bit : (x >> n) & 1.

Toujours le même rituel malloc. Deux cas typiques :

Ce qui distingue ces exercices des précédents : on ne connaît pas la taille du résultat avant d'avoir fait un premier calcul ou un premier passage sur les données. La discipline à adopter est donc toujours la même — d'abord déterminer la taille exacte nécessaire (souvent via un calcul direct, parfois via un premier parcours de comptage), puis seulement allouer et remplir. Céder à la tentation d'allouer « large » ou de remplir avant d'avoir la taille finale est la source numéro un des segfaults de cette famille.

ft_range.c
int *ft_range(int start, int end)
{
    int *tab;
    int i = 0;
    int len = (end >= start) ? (end - start + 1) : (start - end + 1);

    tab = malloc(sizeof(int) * len);
    if (!tab)
        return (0);
    while (i < len)
    {
        tab[i] = (end >= start) ? start + i : start - i;
        i++;
    }
    return (tab);
}

ft_split a la réputation méritée d'être le boss du niveau 3, parce qu'il combine deux notions déjà vues : le parcours par mots (notion 2) et l'allocation à la chaîne (celle-ci). La méthode qui évite de s'y perdre : compte d'abord le nombre de mots en un premier passage, alloue le tableau de char * à cette taille plus un pour le NULL final, puis pour chaque mot — dans un second passage — compte sa longueur, alloue-le individuellement, et copie ses caractères. Trois allocations imbriquées, donc trois vérifications de retour à ne pas oublier. ft_itoa applique la même logique en plus modeste : compte les chiffres du nombre (plus une case pour le signe si négatif), alloue exactement cette taille, puis remplis la chaîne de la fin vers le début — puisque les chiffres se calculent naturellement du poids faible vers le poids fort, comme pour ft_putnbr. N'oublie pas le cas 0 (une seule case, pas de boucle qui tourne zéro fois par erreur) ni INT_MIN, qui se traite comme partout ailleurs en passant par un long.

Notion : Listes chaînées

Exos concernés : ft_list_size, ft_list_foreach, ft_list_remove_if, sort_list.
La structure fournie (recopie-la fidèlement dans ton fichier ou le .h demandé) :

Une liste chaînée n'est jamais qu'un ensemble de maillons qui pointent chacun vers le suivant, jusqu'au dernier qui pointe vers NULL. Toute la famille se résume donc à une seule opération de base — avancer d'un maillon en réaffectant ton pointeur courant à ->next — répétée dans une boucle qui s'arrête sur NULL. Le seul cas qui casse cette routine tranquille est la suppression, parce que retirer le premier maillon signifie changer ce que la tête de liste pointe, et ça, aucune fonction ne peut le faire sans un accès à l'adresse même de ce pointeur de tête.

ft_list.h
typedef struct s_list
{
    struct s_list *next;
    void          *data;
}   t_list;
parcours & foreach
int ft_list_size(t_list *begin_list)
{
    int n = 0;

    while (begin_list)
    {
        n++;
        begin_list = begin_list->next;
    }
    return (n);
}

void ft_list_foreach(t_list *begin_list, void (*f)(void *))
{
    while (begin_list)
    {
        (*f)(begin_list->data);
        begin_list = begin_list->next;
    }
}
remove_if : le double pointeur

En pratique : garde un pointeur « courant » qui parcourt la liste, relie proprement le maillon précédent au suivant avant de supprimer, et surtout — sauvegarde toujours le ->next du nœud avant de le free. Libérer un nœud puis lire son ->next ensuite, c'est lire de la mémoire déjà rendue au système : un classique use-after-free, qui plante parfois, et parfois pas, ce qui le rend particulièrement traître à déboguer.

Vérifie la notion

Voir la réponse

Parce qu'il peut supprimer le premier élément de la liste. Dans ce cas, il faut faire pointer la tête vers le deuxième élément — donc modifier le pointeur du côté de l'appelant. Seul un t_list ** (l'adresse du pointeur de tête) permet cette modification ; avec un simple t_list *, tu ne pourrais changer que ta copie locale, et l'appelant garderait l'ancienne tête (devenue invalide après le free).

Notion : Tri & récursion

Exos concernés : sort_int_tab, sort_list, flood_fill.

Sous le chrono de l'exam, la performance algorithmique ne compte pour rien — un tri en O(n²) sur un tableau de dix entiers est invisible à l'œil, et un tri à bulles tient en huit lignes que tu peux réécrire sans réfléchir. Ne cherche pas à briller avec un tri rapide ou fusion : ici, la simplicité et la fiabilité valent largement mieux qu'une élégance qui augmente le risque de bug. La récursion, elle, mérite plus d'attention : chaque appel récursif doit strictement se rapprocher d'un cas d'arrêt, et ce cas d'arrêt doit être vérifié avant de toucher à la mémoire — jamais après.

sort_int_tab.c — tri à bulles
void sort_int_tab(int *tab, unsigned int size)
{
    unsigned int i = 0;

    while (i < size)
    {
        unsigned int j = 0;
        while (j + 1 < size)
        {
            if (tab[j] > tab[j + 1])
            {
                int tmp = tab[j];
                tab[j] = tab[j + 1];
                tab[j + 1] = tmp;
            }
            j++;
        }
        i++;
    }
}

flood_fill est l'exercice qui montre le mieux la puissance de la récursion sur un problème qui semblerait sinon demander une pile ou une file explicite. Depuis une case (x, y) : si elle contient la couleur de départ, on la remplace par 'F' puis on se rappelle soi-même sur les quatre cases voisines — haut, bas, gauche, droite. La propagation se fait alors toute seule, de proche en proche, jusqu'à ce que toute la zone connexe soit couverte. Ce qui empêche cette récursion de partir en boucle infinie ou de sortir du tableau, ce sont deux conditions d'arrêt vérifiées avant tout accès mémoire : la case doit être dans les limites de la grille, et elle doit encore contenir la couleur de départ (le marquage 'F' fait qu'une case déjà traitée échoue ce second test et stoppe la récursion sur cette branche).

flood_fill.c — cœur récursif
static void fill(char **tab, t_point size, int x, int y, char target)
{
    if (x < 0 || y < 0 || x >= size.x || y >= size.y)
        return ;
    if (tab[y][x] != target)
        return ;
    tab[y][x] = 'F';
    fill(tab, size, x + 1, y, target);
    fill(tab, size, x - 1, y, target);
    fill(tab, size, x, y + 1, target);
    fill(tab, size, x, y - 1, target);
}

void flood_fill(char **tab, t_point size, t_point begin)
{
    fill(tab, size, begin.x, begin.y, tab[begin.y][begin.x]);
}
Vérifie la notion

Dans la fonction récursive fill, quelles sont les deux conditions d'arrêt indispensables ? Que se passe-t-il si tu oublies la première ?

Voir la réponse

1. La case est hors de la grille (x < 0 || y < 0 || x >= size.x || y >= size.y).
2. La case ne contient pas la couleur de départ (tab[y][x] != target).

Sans le test des bornes, la récursion sort du tableau et lit/écrit en mémoire interdite → segfault. Sans le test de couleur, tu ne t'arrêterais jamais aux frontières de la zone (et tu bouclerais à l'infini en repassant sur les cases déjà remplies). Le fait de remplacer par 'F' avant de rappeler garantit aussi qu'on ne revient pas sur une case déjà traitée.

03 Pièges & checklist finale

Une statistique qui devrait te rassurer autant qu'elle t'alerte : la grande majorité des échecs à cet exam ne viennent pas d'un algorithme faux, mais d'un des neuf détails ci-dessous. Autrement dit, savoir coder ne suffit pas — il faut aussi savoir se relire. Passe cette liste avant de rendre chaque exercice, sans exception, même (surtout) quand tu es sûr de toi.

Le \n final

Présent ? En double ? Manquant ? Vérifie avec | cat -e.

argc

« 1 argument » = argc == 2. Le mauvais compte n'affiche qu'un \n.

Chaîne vide

"" est un cas testé. Ton code doit afficher juste le \n.

malloc + 1

'\0' pour une chaîne, NULL final pour un char **.

Retour de malloc

if (!ptr) return (0); systématique.

INT_MIN

-2147483648 : passe par long avant de faire -n.

Warnings

-Werror : signé vs unsigned, variable non utilisée = 0.

Fonction sans main

Sujet « function » → ne rends jamais de main.

Espaces bord

epur/expand/capitalizer : aucun espace au début/fin.

Prototype exact

Type, nom, ordre : recopié à l'identique du sujet.

Routine de test

Prends l'habitude de toujours dérouler la même routine avant de rendre, pour ne jamais avoir à y réfléchir sous pression : compile en local avec cc -Wall -Wextra -Werror ton_fichier.c (en ajoutant ton propre main de test si le sujet demandait une fonction seule), puis compare ta sortie aux exemples du sujet en la passant systématiquement dans | cat -e. Ensuite, pousse volontairement vers les cas limites que la moulinette adore tester : aucun argument, chaîne vide "", un seul caractère, valeurs négatives, zéro. C'est là, et pas dans le cas « normal », que se cachent la plupart des échecs.

{

    int i = 0;

    while (s[i])
    {
        while (s[i] == sep)
            i++;

    }

{

    int  k = 0;

        return (0);
    while (start < end)
        w[k++] = s[start++];
    w[k] = '\0';
    return (w);
}

    int  w = 0;

    {
        while (str[i] == sep)
            i++;
        if (str[i])
        {

            while (str[i] && str[i] != sep)

        }

}
